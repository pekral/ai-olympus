## Concurrency & the working-tree write-lock

This section is the normative contract. `agents/krang.md` is its one executor today and references it by name; nothing here is restated there.

**Worktrees — the writing path stays on the shared tree; a parallel unit and a read-only review may isolate.** **By default the writing path does not use git worktrees.** Every writing run — yours and every concurrent `krang` — operates on the **single shared git working tree** of the project, and concurrent writers serialise on the write-lock below. **Two sanctioned exceptions exist.** The first is a parallel unit (*Parallel units* below): a unit that `skills/_shared/plan-parallel.sh` placed in a batch of two runs `donatello` in its own worktree.
The second is a gate worktree (*Parallel steps against the runs in progress* below): a gate that the planner's step decision sends to its own detached worktree.
Nothing else widens the exception — the orchestrator never creates a worktree for a single unit, for a serial batch, or because a run feels slow.

The **read-only code-review agent (`leonardo`) may use a git worktree** for its review when needed — this is the explicit-request opt-in of `@rules/git/general.md` *Worktrees / Workspaces*, which this workflow grants to the CR pass only. Because the CR agent never writes to the tree, an isolated read-only checkout lets it review a stable diff without contending with the writing path. The read-only security reviewer `splinter` holds the same grant for its own review worktree.
A CR worktree is a throwaway review checkout: the agent reads in it and never edits / commits / pushes there, it records the worktree path in its handoff, and **`krang` removes it during its own *Run cleanup*** (`agents/krang.md` step 7, where that checklist is written down) so nothing orphaned survives the run — including when the run's own turn ends at the `Blocked` stop in step 6 instead of on convergence, which is the path that would otherwise strand the checkout.

Multiple top-level `krang` runs can be launched against the **same project at the same time** (interactively). Because the default writing path uses no worktree, every such writing run shares **one git working tree**. Two runs that both **write** to that tree corrupt each other: `donatello` checks out a branch, edits files, and may `git stash` / `reset` — pulling the tree out from under another run and colliding on uncommitted edits. A run that only **reads** the tree (analysis-only → `leonardo`, or backlog-only, which touches the tracker and never the tree) is safe to overlap.

The fix is a **scope-conditioned write-lock**: only the writing scope (full-delivery → dispatch `donatello`) takes the lock and serialises; the read-only scopes (analysis-only → `leonardo`, and backlog-only run inline) take nothing and stay parallel. The scope signal already exists — it is the classification the orchestrator makes in its step 3 (`backlog-only` vs `analysis-only` vs `full-delivery`).

- **Keyed to the working-tree toplevel.** The lock lives at `.claude/run/.krang-write.lock` (a **directory**), inside the same git-ignored `.claude/run/` of the current toplevel as the shared brief. A default full-delivery run resolves to the **same** toplevel and the **same** lock, so concurrent writing runs contend on it and **serialise** on the shared tree. A parallel unit takes **no** shared-tree write-lock, because it never writes the shared tree (*Parallel units* below). The read-only CR worktree carries no write-lock and never contends here.
- **Atomic acquire.** Create the lock with `mkdir .claude/run/.krang-write.lock` — `mkdir` is atomic and fails when the directory already exists, so it doubles as a test-and-set. On success, write the holder inside it: `PID` — this run's `$PPID`, **never `$$`** (the ephemeral per-Bash-call subshell PID, dead moments after that one tool invocation returns — the same single PID source the orchestrator's startup sweep uses, so every mechanism agrees) — the run's `source-slug`, and `STARTED`, an ISO-8601 timestamp recorded at the moment of this write.
- **Stale reclaim.** When `mkdir` fails, read the holder's `PID` and probe it with `LC_ALL=C kill -0 "$PID" 2>&1` — force the `C` locale so the failure message is always English; on glibc, `strerror()` is locale-translated, and a translated message would silently drop the `"not permitted"` substring the distinction below depends on. `kill -0` conflates "no such process" (ESRCH — genuinely dead) with "process exists, no permission" (EPERM — alive under another UID/namespace); only a failure whose message does **not** mention "not permitted" is a confirmed-dead probe. If the probe is confirmed-dead, the holder is a dead run, the lock is **stale** — `rm -rf` it and re-acquire.
  If the probe finds the PID alive (success, or a failure mentioning "not permitted"), corroborate identity before trusting it as a live blocker — a bare alive PID only proves that PID number is currently in use by *something*, not that it is the same process that wrote `STARTED` (`write-lock-staleness-needs-corroborating-evidence-not-bare-pid` names exactly this gap for the reclaim path).
  Compute that process's own start time from its elapsed run time — `ps -o etime= -p "$PID"` (portable across macOS/BSD and Linux; parse the `[[dd-]hh:]mm:ss` output into seconds and subtract from the current time) — and require it to fall at or before `STARTED`, allowing a small tolerance (e.g. 60 s) for clock/measurement skew: a process cannot have written a timestamp before it existed. When the computed start time is **after** `STARTED`, the PID has been recycled by an unrelated process since the lock was written — identity is **not corroborated**, so treat the lock exactly like a confirmed-dead probe: `rm -rf` it and re-acquire.
  When `STARTED` is absent from the holder file (an older lock predating this field), or `ps -o etime= -p "$PID"` yields no parseable elapsed time (the process exits between the `kill -0` probe and the `ps` call, `hidepid=2`, a PID namespace), the identity check is **inconclusive, not falsified** — treat the lock as held by a live run and report the inconclusive corroboration, mirroring the fail-safe default the orchestrator's startup sweep applies to a missing or malformed `## PID`; only a *successfully computed* start time **after** `STARTED` justifies reclaiming the lock.
  Only when the alive probe **and** the identity check both hold does a live full-delivery run genuinely hold this working tree: **do not proceed into `donatello`**.
- **Release.** Remove the lock (`rm -rf .claude/run/.krang-write.lock`) during *Run cleanup* — on the final report **and** on any `Blocked` stop — right next to the existing `rm -f "$BRIEF"`, so no orphan lock survives the run.

Only the full-delivery path acquires and releases the lock. An analysis-only run never touches it, so any number of `leonardo` security-analysis runs overlap freely with each other and with one writing run.

**Processing of multiple sources — sequential by default, two at a time only when the planner proves it safe.** When a **single request resolves to multiple sources** (e.g. "analyse these issues", a batch of links, or several sub-issues), `krang` runs `skills/_shared/plan-parallel.sh` over them (`agents/krang.md` step 1, *Plan parallel batches*) and processes the resulting **batches one after another**. A batch holds one or two units. Finish a batch completely (every unit's convergence gate satisfied and its brief cleaned up) **before** starting the next. Order the sources by the dependency-aware plan from the orchestrator's step 1 when they are interlinked (dependencies before dependents), otherwise oldest-first.

- **A single-unit batch is the old behaviour, unchanged.** It runs on the shared tree under the shared write-lock, one `Task` at a time.
- **A two-unit batch is the only fan-out.** The orchestrator dispatches both units' `donatello` runs as two blocking `Task` calls in **one** message. Never fan out analysis-only `leonardo` runs, never dispatch more than two `Task` calls in one message, and never start a unit of the next batch while the batch is open.
- **Each source gets its own shared brief** (`.claude/run/<source-slug>.md`, one per source — the slug is already per-source), its own dispatch ledger, and its own audit trail. Report the batch only after **every** source has finished its run.
- **The planner decides, never the orchestrator.** Two units overlap only when `plan-parallel.sh` says `mode.<k>=parallel`: their predicted changed-file sets are disjoint, neither depends on the other, neither is `CRITICAL` in `skills/_shared/classify-risk.sh`, and the batch holds at most **2** units. That limit is fixed in the script and the manifest has no key for it. A unit with no file evidence runs alone. The orchestrator records the file evidence per unit in the brief, because a plan without evidence is a guess.

## Parallel units

A parallel unit is one `donatello` implementation run in a batch of two. It is isolated on disk and it shares the machine's scarce resources through locks.

- **Worktree per unit.** The dispatch prompt names the worktree path `.claude/worktrees/agent-impl-<source-slug>-donatello` and the unit's branch. `donatello` creates it from the default branch (`git worktree add -b <branch> <path> origin/<default>`), locks it with the reason `pid $PPID agent donatello slug <source-slug>` so the startup sweep (`skills/_shared/orchestration/stale-run-recovery.md`) can tell a live worktree from a dead one, and runs every command of the unit inside it. The shared tree is not touched.
- **No branch switch in the shared tree.** Git refuses to check out a branch that another worktree holds, and the unit's worktree holds the unit's branch from its creation until its removal. Every step of the unit that would switch a branch runs in the worktree instead: `resolve-issue` skips its default-branch switch, and the review-and-fix rounds and *Finalization* of `@skills/process-code-review/SKILL.md` receive the worktree path and use `git -C <path>`. The dispatch of each of those steps names the path (`agents/krang.md` step 6).
- **Removal.** `@skills/merge-github-pr/SKILL.md` *Post-merge* removes the worktree after the merge. A run that ends before a merge removes it in *Run cleanup* (`agents/krang.md` step 7) once it is clean and its `HEAD` is on the remote branch, so the work survives and no worktree is stranded. Never `--force`.
- **The worktree is the unit's lock.** A unit takes no write-lock. `git worktree add` fails when the path or the branch already exists, so a second run of the same source cannot enter the worktree of the first: it stops with `Blocked: another run holds this unit's worktree`.
- **At most two units, and no more heavy work than one.** Gate runs, dependency installs (`composer install`, `npm ci`), and full test suites are **never concurrent** between units, between worktrees, or between runs. They take the one machine-wide lock below. A diff-targeted check (Pest, Rector, or PHPStan on a path list, the validation manifest) takes it too: it is a heavy command, because each of those tools starts worker processes.

## Parallel steps against the runs in progress

`krang` decides every step against the work other runs are doing in the repository now, not only against the units of its own request. The decision has one owner: `skills/_shared/plan-parallel.sh --step`. `krang` gathers the evidence and the script decides. `krang` never judges alone that a step may overlap another run.

- **Which steps.** Every step `krang` dispatches. The writing steps are the implementation, a review-and-fix round, and *Finalization*. The heavy steps are a gate run, a dependency install, and a full test suite. A read-only step goes through the same decision and starts beside a live writer, as *Concurrency & the working-tree write-lock* allows. A unit of a two-unit batch is a step too: when its decision is `wait`, the batch runs its units one after the other.
- **Live runs.** `krang` writes one `live|<id>|<kind>|<tree>|<branch>|<files>` line per run in progress, never one for its own run. The sources are the briefs in `.claude/run/` whose `## PID` is not confirmed dead (the probe of `skills/_shared/orchestration/stale-run-recovery.md`; an unparseable `## PID` counts as live), the holder of the write-lock, the worktrees whose lock reason names a live `pid <N>`, and the holder of the gate lock.
  - A brief gives the run id (its slug), the tree `unknown`, the files of its `## Plan & work breakdown`, and the kind `write` for a full-delivery run.
  - The write-lock holder gives the kind `write` in the tree `shared`.
  - A locked worktree gives its path as the tree, its branch, and the kind of the agent in the lock reason: `read` for `leonardo`, and `write` for every other role, including a role this rule does not name. A locked worktree whose reason carries no valid `pid <N>` token counts as live with the kind `write`, as `skills/_shared/orchestration/stale-run-recovery.md` *Stale worktrees* leaves it in place.
  - The holder of the machine lock gives the kind `heavy`. Its holder file names the project and the command and records no tree, so the tree is `unknown`, which the planner counts as the shared tree.
- **Ledgers.** The ledgers of a run (the brief, `.dispatches`, `.audit`, `.routing`) are keyed to its slug, and no run writes the ledger of another. A step that writes a ledger beside another run puts that ledger in the file list of its own line and in the file list of the other run's `live` line, so the planner sees the collision.
- **Unreadable evidence is a wait.** A missing `live` line never means an idle machine. Each case below gives `decision=wait`, and `krang` does not dispatch:
  1. An evidence source it cannot read.
  2. A lock directory with no readable holder file. `skills/_shared/gate-record.sh` writes the holder after its `mkdir`, so the run that made the lock is live.
  3. A planner that exits non-zero.
  `krang` writes the unreadable source, the lock path, or the planner message as the `reason` in the brief.
- **Project memory.** `krang` runs no memory read for a step decision. When *Critical-finding memory read* (`agents/krang.md`) already ran in this run, each returned entry whose `paths` names a file every write run changes gives one `shared|<path>|<slug>` line, after `git ls-files` confirms the path. Without that read the input carries no `shared` line. The memory adds a block and never lifts one.
- **The decision.** `decision=parallel` means `krang` dispatches the step now. `decision=wait` means it does not dispatch and writes the `blocker` and the `reason` into the unit's `## Plan & work breakdown`. It never overwrites, resets, or switches the tree or the branch of another run to get past a wait. The result is a snapshot: the write-lock, `git worktree add`, and the gate lock stay the enforcement, and `krang` gathers the evidence again before each decision.
- **A wait has one end.** A wait ends in one of two ways, by the kind of blocker.
  1. **The blocker is a unit of this request.** `krang` dispatched its run and receives its handoff. `krang` decides again after that handoff, at most three decisions in total, the first included. A step that still waits after the third decision stops with `Blocked`, naming the blocker and the `reason`.
  2. **The blocker is another run, a lock, or unreadable evidence.** When the lock is the machine lock, `krang` first checks it and repairs a dead or stuck holder (`skills/_shared/orchestration/stale-lock-repair.md`), then decides once more. No handoff of the blocker reaches `krang`: another top-level session never reports to this one, and a lock or an unreadable source has no run at all. `krang` stops with `Blocked` at once, naming the blocker and the `reason`, and states the remedy: start the request again when the blocker is gone.
  In both cases `krang` runs *Run cleanup* (`agents/krang.md` step 7) before the stop, as step 5 does for its own stop.
- **The write-lock holder is not a second wait.** This applies to a `write` step. When the blocker is the live holder of the write-lock, the stop of `agents/krang.md` step 5 (`Blocked: another krang writing run holds this working tree`) is the end of the wait, and `krang` does not decide again for it. A `heavy` step first takes the gate-worktree decision of *A gate beside other runs*, because a gate in its own worktree needs no write-lock.

### A gate beside other runs

- **A gate is a `heavy` step.** The planner answers `parallel` with `lock=gate` when no live run is heavy and no live writer holds the gate's tree. The gate then takes the machine lock when it starts, so two gates never run at the same time. A `heavy-job` wait names the holder of that lock.
- **The gate worktree.** When the answer for the shared tree is a `tree-in-use` wait, `krang` decides again with the tree `.claude/worktrees/agent-gate-<source-slug>`.
  - **Scope.** The run that executes the gate runs the `pr` tier only, never *Finalization*: a gate that fails, or leaves the worktree dirty, is reported, and every fix is made in the unit's own tree.
  - **Creation.** The run creates the worktree with `git worktree add --detach <path> <head-sha>`, locks it with the reason `pid $PPID agent <role> slug <source-slug>`, installs the dependencies through `skills/_shared/run-gate.sh --exclusive --command "<command>"`, and runs the gate inside it. A detached worktree holds no branch, so it never blocks the branch of the unit.
  - **Handoff.** The run records the worktree path in its handoff and stops `Blocked` when `git worktree add` fails.
  - **Removal.** The run leaves the worktree in place and records its path in its handoff. `krang` removes `.claude/worktrees/agent-gate-<source-slug>` in *Run cleanup* (`agents/krang.md` step 7), under the clean check and the confirmed-dead probe, unlocking it first because its lock reason names the `$PPID` of the run, and never with `--force`. A subagent hands the path back and removes nothing, as `@rules/git/general.md` *Clean up after the task — on every terminating path* states.
- **The record is discarded with the worktree.** A gate record lives in the evidence directory of the tree that ran the gate, so removing the worktree discards it. The full-tier record the merge accepts stays the one `skills/_shared/verify-gate.sh` finds for the exact head commit being merged.

## One gate lock for the machine

All heavy work goes through one lock, `ai-olympus-gate.lock`, a directory in the machine directory `${XDG_CACHE_HOME:-$HOME/.cache}/ai-olympus` (`AI_OLYMPUS_LOCK_DIR` moves it; `skills/_shared/gate-record.sh` `gate_machine_dir` owns the path). The directory is outside every repository, so every project, the shared tree, and every worktree of the account contend on the same lock. This is a different lock from the write-lock: the write-lock protects one tree's files, and this lock protects the machine's CPU, memory, and test database. The lock is per user account: two accounts on one machine do not share it.

- **Same mechanics as the write-lock.** Atomic `mkdir`, a holder file, and a reclaim only on a confirmed-dead probe or a recycled PID (`skills/_shared/gate-record.sh` `gate_lock_is_stale`). The holder file carries `PID`, `STARTED`, `STARTED_EPOCH`, `PROCESS_START` (the start of the holder process), `WRAPPER` (`run-gate.sh` or `run-validation.sh`), `PROJECT`, and `COMMAND`. An inconclusive probe counts as a live holder. A holder that exited and no parent reaped (a zombie) counts as dead. Only one waiter reclaims: it takes a `<lock>.reclaim` directory (atomic `mkdir`), checks staleness again under it, removes the lock, and releases the reclaim directory. A waiter that read the dead holder earlier then does not remove a live lock another waiter took in the meantime.
  - The reclaim directory has its own holder file (written without overwriting an existing file) and is removed only when that holder is confirmed dead by the same probe, so no waiter that probes a stopped but alive waiter's directory removes it.
  - One race stays open, because `mkdir` has no compare-and-delete and `flock(1)` does not exist on macOS. A waiter that probed a dead reclaim directory and stalls before it removes it can remove a newer waiter's live one. Two gates then run at once only when that newer waiter also stalls between its second probe and its removal of the gate lock, so the race needs a dead gate holder, a dead reclaimer, and two stalled waiters.
  - A reclaim directory without a readable holder file counts as live for one minute, because the waiter is between its `mkdir` and its holder file. After that minute the waiter was killed in that window, and the directory is removed.
- **Callers wait; they do not fail fast.** A caller waits for a live holder up to `AI_OLYMPUS_GATE_LOCK_TIMEOUT` seconds, **3600** by default — longer than a full gate takes, so a unit queued behind another unit's full gate waits instead of failing.
  While it waits, it prints the holder it waits for (PID, project, command, start) to stderr every minute. Only a wait past the timeout exits `6`, and the caller then stops and reports (`skills/resolve-issue/references/quality-gates.md` *Machine gate record*). The tool that runs the call ends it sooner than the timeout (120 s by default, 600 s at most), so the caller runs the gate in the background or with the maximum tool timeout and runs it again, a bounded number of times, when the harness stopped it — never as exit `3` (`skills/resolve-issue/references/quality-gates.md` *Waiting for the gate lock*).
- **Every heavy command takes it.** `run-gate.sh --tier pr` and `--tier full` hold it for the run. Their per-tree record and take-over stay per working tree, so a unit that waited does not run again a gate whose record exists in its own tree.
  `skills/_shared/run-validation.sh` holds it from its first command to its last, and an agent runs every targeted check (Pest, Rector, PHPStan, the other validation executables, a coverage run) through `run-gate.sh --exclusive` (`skills/resolve-issue/references/quality-gates.md` *Targeted checks take the machine lock too*). A command that a holder started inherits `AI_OLYMPUS_LOCK_HELD_BY=<holder PID>` and runs under that lock instead of waiting for it.
- **A project without a manifest gate takes it through `--exclusive`.** When `run-gate.sh --tier ...` exits `5`, the caller runs the discovered gate command, the dependency install, the full test suite, or a targeted check through `skills/_shared/run-gate.sh --exclusive --command "<command>"` (repeat `--command` for an ordered list). It runs the commands as an argv without a shell under the same lock, writes no record, and exits `0` passed, `3` refused, `4` a command failed, `6` the lock timed out.
- **A stuck holder is repaired, not waited out.** The holder runs a heartbeat beside the command (`skills/_shared/gate-lock.sh heartbeat`). Every `AI_OLYMPUS_GATE_HEARTBEAT_INTERVAL` seconds (30 by default) it samples the CPU of the holder's process tree and the set of processes in it, and the `heartbeat` file in the lock names the last time the sample changed. A holder that is alive and shows no change for `AI_OLYMPUS_GATE_STUCK_AFTER` seconds (1800 by default) is **stuck**. A waiter never reclaims it, because its process is alive. `krang` repairs it with `skills/_shared/gate-lock.sh repair`, at the start of a run and when a dispatch or the validation runner reports the lock (`skills/_shared/orchestration/stale-lock-repair.md`).
  - **What repair may stop.** Repair stops one process tree, the holder and its descendants, and only when a wrapper of this package started that holder. It proves that with the recorded PID, the wrapper name in the holder file, the command line of the live process, and the recorded process start. A recycled PID, another program, or a holder file of an older format fails the proof: nothing is stopped, the lock stays, and the exit is `3`. It never stops a process the wrapper did not start.
  - **What repair records.** It writes one line to the run's audit ledger (`rules/compound-engineering/orchestration.md` *Audit trail for memory reads, outbound requests, and external writes*): an `external-write` line for a released lock, a `note` line for a refusal.
  - **Known limit.** A holder that keeps using CPU while it makes no useful progress (an endless loop) counts as progress and is never repaired. The limit of such a run is the caller's timeout.
