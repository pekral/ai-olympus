# Code Review — Specialized Reviews

Referenced from `@skills/code-review/SKILL.md` *Specialized Reviews*. The sets below were extracted from the skill body to keep the skill within the skill-check token budget; the skill references them by name. Run them exactly as if they were inline in the review skill.

## Specialized Reviews

- Always run:
    - @skills/prepare-issue-context/SKILL.md with `MODE=cr` **as a pre-flight before any other specialized review** — audits whether the dev database currently holds the fixture data the assignment scenarios need, and surfaces every scenario the diff *should* cover but the codebase / dev DB cannot reproduce. The CR uses its gap report to ground the rest of the review in real data; an empty gap report means later findings (assignment compliance, security, refactoring) are made against scenarios that genuinely exist, not against guesses. Surface the gap count in the PR comment summary line and treat any **behavioral gap** the skill reports as a **Critical** CR finding (the diff cannot satisfy a scenario the codebase does not support).
    - @skills/assignment-compliance-check/SKILL.md — verifies the PR implementation satisfies the business requirements stated in the linked issue / task. The skill **does not publish anywhere itself** — it returns either the assembled `## Assignment Compliance` markdown block (only when at least one Critical gap exists), the status `no critical gaps — assignment compliance block omitted` (when the implementation satisfies every stated requirement), or the status `no linked issue — assignment compliance skipped` (when no linked tracker exists).
The CR wrapper passes the returned block as an embedded block to `@skills/pr-summary/SKILL.md` **only when a block is returned** so each linked tracker (GitHub issue or JIRA ticket) receives **one consolidated comment** per CR run (per issue #498); on either skip status the wrapper embeds nothing and surfaces the status on the PR comment summary line. **Do not embed** the block into the PR comment — that comment carries technical findings only.
    - @skills/analyze-problem/SKILL.md — **always run, scoped to assignment conformance.** Run it **inline in this skill's context** (do not dispatch as a subagent) against the issue context already loaded under **Issue Context Analysis** (requirements, acceptance criteria, expected behavior, edge cases, test data) and the PR diff, to answer one question: does the implemented code actually deliver what the assignment asked for? Walk the framework's steps 1–3 only — **Context extraction**, **Problem statement** (reframed as *the assignment*: what the code must do), and **Expected vs actual behavior** (the assignment-required behavior vs what the diff actually implements).
Treat every required behavior the diff fails to deliver — a missing behavior, a wrong behavior, an acceptance criterion left unimplemented, a stated edge case or sample test scenario not handled — as a **Critical** finding (the code does not satisfy the assignment) carrying the standard reproducer fields (Faulty Example / Expected Behavior / Test Hint / Suggested Fix). **Read-only invocation:** within the CR the skill runs analysis-only — it returns the gap findings as markdown and must **not** write the *Pre-Implementation Research & Plan* artifact, modify code, or run any git write (the CR is read-only); skip the plan-artifact step entirely.
This is **distinct from** the per-Critical-finding **Critical Findings Verification (issue #537)** below, which uses the same skill to *confirm* each Critical finding one by one; here the skill runs **once over the whole diff** to *detect* assignment gaps up front. Do not duplicate a gap that `@skills/assignment-compliance-check/SKILL.md` already raises in its `## Assignment Compliance` block — when both would surface the same gap, keep the technical **Critical** finding here (with reproducer fields, published under `## Functional Review` per the Two-Part CR Output contract) and let the compliance block carry only the non-technical mirror.
    - @skills/security-review/SKILL.md — **skipped when `SECURITY_OWNER=athena` is set by the caller.** When a **separate, concurrent** agent owns the security review, this inline pass repeats the same full review over the same diff and lands the same findings twice; the always-run set is strictly sequential, so the duplicate is pure added latency, not added coverage. **Absence of the flag means it runs** — coverage never drops because someone forgot to set it, and a run with no concurrent security pass is unchanged. **No agent this package ships sets the flag** (issue #179): `athena` is the single reviewer, so this inline pass *is* her security pass and suppressing it would skip the review with nothing behind it.
The flag is for an external caller that genuinely runs a concurrent pass. When it is skipped, say so on the summary line (`security: owned by athena`) so the PR comment never implies a security pass that did not happen here.
    - @skills/api-review/SKILL.md — API design contract lens (`@rules/api/general.md`). The skill self-scopes: when the diff touches no HTTP API surface (routes, controllers / `__invoke` request handlers, API Resources / DTOs in responses, FormRequests, status-code handling, `Idempotency-Key` logic) it returns no findings. When it does, fold the Critical / Moderate / Minor findings (with their reproducer fields) into the standard severity buckets — do not duplicate a finding the **Strict rule compliance** walk already raised for `@rules/api/general.md`.
    - @skills/class-refactoring/SKILL.md **with `MODE=cr`** — read-only refactoring lens scoped to the PR diff. Use it to surface concrete tech-debt-reducing changes (DRY duplication, single-responsibility breaches, oversized methods) that apply to lines actually touched by the PR. `MODE=cr` guarantees the lens never modifies code, writes tests, commits, runs fixers, or chains another review — it returns proposals only. Do not propose changes that fall outside the diff.

- Run conditionally:
    - **Diff is a refactoring (behavior-preserving structural change per `@rules/refactoring/general.md`) → run the full refactoring skill set read-only.** Detect this when the PR restructures existing code without adding a feature or changing observable behavior (extracted methods / classes, moved orchestration, renamed-for-clarity, dedup, layer reshuffles). When it fires, additionally invoke `@skills/refactor-entry-point-to-action/SKILL.md` **with `MODE=cr`** (and run the `class-refactoring` lens above at full depth) to surface the entry-point → Action proposals.
**Both skills run read-only — no code changes, no commits, no fixers, no review chaining — `MODE=cr` enforces this.** Fold their output into the **Refactoring (DRY / tech debt)** section (in-scope items) and **Refactoring proposals** section (out-of-scope items) of the review; this skill never modifies code.
    - **Database operations detected in the diff → exactly one DB lens is mandatory.** Trigger the DB lens whenever the diff touches any of: raw SQL strings, Eloquent / query-builder calls (`DB::`, `->where(`, `->join(`, `->whereHas(`, `->withCount(`, `->orderBy(`, `->groupBy(`, `->chunk(`, `->cursor(`, `paginate(`, `simplePaginate(`), Eloquent relationship definitions, `with(` / `load(` eager loads, model scopes, ModelManager / Repository methods, database migrations (`Schema::`, `up()` / `down()`), seeders, factories that materialise rows, DynamoDB / NoSQL access. The pattern list is engine-independent: it decides *whether* a DB lens runs, and the engine decides *which one*. A diff matching none of those patterns runs no DB lens at all.
**Resolve the engine deterministically, never by guessing**, from the first of these sources that answers: (1) `config/database.php` — the `default` connection, then that connection's `driver`; (2) `DB_CONNECTION` in `.env.example`, the committed template, never a developer's own `.env`, which the repository does not carry — reading that one template is the named exception `@rules/compound-engineering/orchestration.md` *Bash capability boundary* carves out of its `.env*` read ban; (3) the driver / DBAL package required in `composer.json`. A project with several connections is decided by its **default** connection, never by the presence of a second one. Never read the engine off a table name, a column type, or the wording of the diff.
**Source (1)'s `default` key is usually not a literal, so read it in two steps.** The framework's own skeleton ships `'default' => env('DB_CONNECTION', 'sqlite')` — an environment lookup, not a driver name. When `default` is an `env('DB_CONNECTION', <fallback>)` call, resolve the connection **name** through source (2) first, and take the `env()` fallback literal only when `.env.example` carries no `DB_CONNECTION`. The fallback states what applies when the environment sets nothing, while `.env.example` records what the environment does set, so reading the fallback first answers `sqlite` on a stock PostgreSQL project and never reaches sources (2) or (3) at all. Once the connection name is known, its own `driver` key in `config/database.php` is a literal and is read directly.
**This one resolution step has two consumers, not one.** The MySQL schema-feature trigger below reads the same answer, and its own pattern list is broader than this trigger's, so a diff can fire that trigger while none of the patterns above match. On such a diff the step has not run yet, and that trigger runs it — the same sources, in the same order, still exactly one resolution per review. Whoever edits the sources above edits them for both readers.
        - **`mysql` / `mariadb` → `@skills/mysql-problem-solver/SKILL.md`.** Identical to the behaviour before this branch existed: the same lens, the same findings, the same section.
        - **`pgsql` → `@skills/postgres-patterns/SKILL.md` with `MODE=cr`.** `MODE=cr` is that skill's read-only contract — it returns findings as markdown and never writes a migration, an index, or a configuration change. Its deploy-safety half is what `@rules/code-review/core-analysis.md` *Deploy-safe schema changes (issue #20)* redirects a PostgreSQL project to: the **Suggested Fix** for a blocking index build is `CREATE INDEX CONCURRENTLY` with the migration's wrapping transaction disabled (`public $withinTransaction = false;`), never `ALGORITHM` / `LOCK`, which PostgreSQL does not parse.
        - **Engine not resolvable, or resolved to any other driver (`sqlite`, `sqlsrv`, …) → `@skills/mysql-problem-solver/SKILL.md`**, the pre-existing default, so a project carrying no `config/database.php`, and a project on a driver this list does not name, both review exactly as they do today. This branch is the catch-all: every outcome of the resolution step lands in exactly one of the three branches, and no diff is ever left with no lens.
          The review then states the assumption per `@rules/code-review/general.md` *Safety*, on the summary line — the conditional `Assumption:` slot both render templates define for it (`skills/code-review/templates/review-output.md`, `skills/code-review-github/templates/pr-comment-output.md`) — in whichever of the two forms fits the case: `Assumption: database engine not resolved from config/database.php, .env.example, or composer.json — reviewed with the MySQL lens.` when no source answered, and `Assumption: database engine resolved to <driver>, which has no dedicated lens — reviewed with the MySQL lens.` when a driver answered but is neither MySQL / MariaDB nor PostgreSQL. The silent fallback is what this branch exists to prevent, not the fallback itself.
        - **Never run both lenses on the same diff.** The branches are mutually exclusive by construction: the engine resolves to exactly one value, and the catch-all branch names exactly one default for every value the two named branches do not claim. Running both would report one query defect twice under one `## Database Analysis` heading, at two severities, from two engines' semantics.
Pass the diff scope to the resolved lens and capture its findings — they **must** appear in the published CR review under the single dedicated `## Database Analysis` section described in **Output Rules**, whichever lens produced them, never silently absorbed into the generic Critical / Moderate / Minor buckets.
    - **MySQL schema-feature surface detected in the diff → the schema-pattern lens runs.** Trigger it whenever the diff adds or modifies any of: a migration (`Schema::create` / `Schema::table` / a raw DDL statement), an upsert (`upsert(`, `insertOrIgnore(`, `updateOrCreate(`, `ON DUPLICATE KEY UPDATE`), a JSON column or JSON path (`->json(`, a `storedAs(` / `virtualAs(` generated column over a JSON path, `whereJsonContains(`, an `attributes->` path), a full-text index or match (`fullText(`, `whereFullText(`, `MATCH … AGAINST`), a partition definition (`PARTITION BY`, `ADD PARTITION`), deadlock handling (`DB::transaction(…, attempts:)`, a caught SQLSTATE `40001` / error `1213`, `lockForUpdate(`, `SKIP LOCKED`),
or read/write splitting (a `read` / `write` / `sticky` key under a `config/database.php` connection, `->onWriteConnection()`).
That pattern list is the whole gate and it decides *whether* the lens runs: **a diff matching none of those patterns runs no schema-pattern lens at all** — a query change that touches none of those features is the DB lens's business alone.
**This lens hangs on the one engine resolution the DB-lens trigger above defines — it never defines a second one.** Two independent resolutions in one review can disagree, which is why there is exactly one resolution step — the `config/database.php` → `.env.example` → `composer.json` sequence above — and this trigger reads its answer.
**When the DB-lens trigger did not fire on this diff, that answer does not exist yet, so this trigger runs that same step itself.** This trigger's pattern list is deliberately broader than the DB lens's: a `read` / `write` / `sticky` key under a `config/database.php` connection, and a caught SQLSTATE `40001` / error `1213` outside any query call, match nothing in the DB-lens list, so such a diff arrives here with no engine resolved.
Running the one defined step here is not a second resolution — it is the same step, by the same sources, in the same order, producing the single answer this review has. One resolution per review, owned by whichever trigger fires first, and that owner also writes the `Assumption:` line the unresolved branch below requires. Branch on that answer:
        - **`mysql` / `mariadb` → `@skills/mysql-patterns/SKILL.md` with `MODE=cr`.** `MODE=cr` is that skill's read-only contract — it returns findings as markdown and never writes a migration, an index, or a configuration change.
        - **`pgsql` → the lens does not run, silently.** MySQL syntax is not a defect to report on a PostgreSQL project, whichever trigger resolved the engine. When the DB-lens trigger also fired, `@skills/postgres-patterns/SKILL.md` is already running as this diff's DB lens and owns the Postgres counterpart of every feature in the list (jsonb and GIN, `ON CONFLICT`, declarative partitioning, `tsvector` search); when only this trigger fired, the diff carries none of the query patterns a DB lens reads, so no lens runs on it and none is missing. Either way the skip is not an error and is **not reported**: no finding, no section, no summary-line slot, no "skipped" placeholder.
        - **Engine not resolvable, or resolved to any other driver (`sqlite`, `sqlsrv`, …) → `@skills/mysql-patterns/SKILL.md` with `MODE=cr`**, following the DB lens into its own catch-all so one engine answer never produces two different consequences. The assumption goes on the summary line **once**, in the single conditional `Assumption:` slot the two render templates already define, written by whichever trigger resolved the engine: when the DB-lens trigger fired, its own catch-all already wrote that line and this lens adds nothing; when only this trigger fired, this lens writes it, verbatim in the same two forms that branch defines.
**Never state it twice**, and never add a second `Assumption:` slot for this lens. This branch is the catch-all: every outcome of the single engine resolution lands in exactly one of the three branches above, so no schema-feature diff is ever left with no lens.
        - **This lens is not a fourth engine branch.** The *Never run both lenses on the same diff* rule above does not reach it. That rule governs the two mutually exclusive *engine* lenses, `mysql-problem-solver` and `postgres-patterns`, and forbids reading one diff through two engines' semantics. The schema-pattern lens is a second *dimension* over the one resolved engine, not a second engine, so on MySQL / MariaDB it runs **alongside** `mysql-problem-solver`, never instead of it.
Fold its findings into the same single `## Database Analysis` section the engine lens fills — never a second section, never a per-lens variant, and never silently absorbed into the generic Critical / Moderate / Minor buckets.
**Gating — one finding per violation, never two.** `@skills/mysql-problem-solver/SKILL.md` reads the same diff on a MySQL project. **That lens owns the performance of a query and its plan** — index usage, rows examined, `EXPLAIN` shape, `filesort` / `temporary`, and the non-regression gate on a rewritten query. **The schema-pattern lens owns the shape of the feature** — whether the upsert is one statement over a backing unique index, whether the JSON path is indexed through a generated column, whether the partition key matches the predicate, whether `sticky` survives a read-after-write path, whether the concurrent transaction carries a deadlock retry.
The two divide the *dimensions* of a DB change, never its lines: a slow query over a new partition carries one performance finding from `mysql-problem-solver` and one partition-shape finding from `mysql-patterns`. What neither does is restate the other's finding in its own words.
    - **Frontend surface detected in the diff → all three frontend lenses run.** Trigger them whenever the diff adds or modifies any of: a `*.blade.php` file anywhere in the tree, a Livewire component class under `app/Livewire/**`, any file under `resources/views/**`, a Filament resource / page / widget / form schema under `app/Filament/**`, a stylesheet or Filament theme under `resources/css/**`, or the Tailwind configuration (`tailwind.config.js` / `tailwind.config.ts`, or a `@theme` block in the CSS entrypoint).
That pattern list is the whole gate and it decides *whether* the lenses run: **a diff matching none of those patterns runs no frontend lens at all** — a change confined to `app/Models/**`, a migration, or a console command never triggers one. The gate is independent of every other conditional trigger, so a diff that touches a Blade view *and* a migration runs the frontend lenses and the engine-resolved DB lens side by side.
**One trigger, three lenses, three responsibilities.** All three run together whenever the trigger fires; none is conditional on another, and none may be dropped because another already looked at the same file. Each runs **with `MODE=cr`**, that skill's own read-only contract — the lens returns findings as markdown and never edits a view, a component, a token, a config, or a theme.
        - **`@skills/frontend-patterns/SKILL.md` with `MODE=cr`** — component composition, where state lives (Livewire vs Alpine), render and network cost, form mechanics, and whether the loading / empty / error / offline states exist and behave.
        - **`@skills/frontend-a11y/SKILL.md` with `MODE=cr`** — semantic markup, label and error association, keyboard operability, focus management, live-region announcement of Livewire updates, and the contrast of the token pairs the changed markup uses.
        - **`@skills/design-system/SKILL.md` with `MODE=cr`** — Tailwind token and Filament theme consistency, reuse of the shared `<x-ui.*>` component set, `dark:` completeness, and the AI-slop patterns.
        - **Project is not Laravel → skip all three, silently.** Resolve this exactly as the architecture walk does — `laravel/framework` is absent from `composer.json` `require` (`@rules/code-review/core-analysis.md` *Architecture conformance (Laravel)*). All three lenses are written for the Blade / Livewire / Alpine / Filament / Tailwind stack and have nothing to read on any other one. The skip is not an error and is **not reported**: no finding, no section, no summary-line slot, no "skipped" placeholder — exactly like the `## Architecture` section the same detection already omits.
        - **Laravel project missing a package a lens assumes — no Livewire, no Filament, or neither → all three still run, each narrowed to the surface that exists.** Judge the Blade and Tailwind the project does have, and never raise a finding whose fix is to adopt Livewire, Filament, or Alpine — the absence of a dependency is a project decision, not a defect on the diff. `frontend-a11y` is unaffected by any of them, because semantic markup, labels, and keyboard operability do not depend on a package.
        - **Every other outcome runs all three.** This is the catch-all: a Laravel project whose diff matches the pattern list lands here, so every outcome of the detection step falls into exactly one of the three branches above and no frontend diff is ever left with no lens.
Fold the findings of all three lenses into the standard **Critical / Moderate / Minor** buckets of `## Findings`, each carrying the usual reproducer fields (Faulty Example / Expected Behavior / Test Hint / Suggested Fix). This trigger introduces **no** new report section and **no** new summary-line slot, so no render template changes for it; the CR wrapper contract does not restate this trigger for the same reason — there is no wrapper-specific publishing surface to describe, unlike the DB lens's own `## Database Analysis` section.
**Gating — one finding per violation, never two.** The walk *Livewire / Blade layout splitting* (`@rules/code-review/review-process.md` *Refactoring & Tech Debt (DRY) Analysis*, triggers in `@rules/laravel/livewire.md` *HTML / Blade Layout Splitting*) already runs over every `*.blade.php` file on the same diff, so the two sides must divide the markup rather than both report it. **The walk owns where the markup is split** — whether a block becomes its own component, which type it must be (Livewire vs Blade), where it lives, what it is named, and the reusability contract it has to satisfy. **The three lenses own what is inside the component**, once that split question is settled. The three places they meet resolve to one owner each:
        - A region rendering its own `wire:loading` / `@empty` / error banner inline (walk trigger 6) — the walk owns the *extract this region* entry; `frontend-patterns` owns *this state is missing entirely, or it behaves wrong* and never restates the extraction.
        - A self-contained `wire:model` / `wire:click` / `wire:submit` cluster left inline (walk trigger 3) — the walk owns the *extract this cluster* entry; `frontend-patterns` owns which layer the state belongs on and which `wire:model` modifier it uses, once the cluster sits where the walk says.
        - A structural HTML block repeated two or more times (walk triggers 1 and 5) — the walk owns the *extract this block* entry; `design-system` owns the token or theme inconsistency between the copies and never restates the extraction.
        - A block whose only defect is that it is not yet its own component — a view over 150 lines of markup, a `@foreach` body over roughly 10 lines per iteration, or a region carrying a name a designer would use (walk triggers 2, 4, and 7) — the walk owns it whole, and no lens has a second half to add. **No lens ever raises a finding whose fix is *create a component*.** A lens speaks about a component that already exists; the walk decides that one should exist. Together with the three points above, this covers every one of the walk's seven triggers, so no trigger is left with two possible owners.
**Never raise two of the three lenses on the same line either.** This sentence divides the three lenses against each other; it never re-opens the walk's half of the boundary above. `frontend-a11y` is the sole owner of every accessibility finding, contrast included — `design-system`'s contrast dimension and `frontend-patterns`' form work both defer to it. `design-system` is the sole owner of token and theme consistency, and of the hover and transition half of its own *Polish* audit dimension.
`frontend-patterns` is the sole owner of state placement, render cost, form mechanics, and the loading / empty / error states — that last surface is the half of `design-system`'s *Polish* dimension that lens defers here, so a missing `wire:loading` or `@empty` is this lens's finding and never a token one — and, among the three lenses, of composition **inside a component that already exists**, never of the decision that a block should become one.
