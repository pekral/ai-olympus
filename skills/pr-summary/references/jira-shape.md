# The JIRA shape

Referenced from `skills/pr-summary/SKILL.md` *The JIRA shape*. This file owns the shape of every JIRA comment `pr-summary` renders; `templates/pr-summary-jira.md` renders it.

A JIRA ticket is read by the person who asked for the work, so the report lists only what still needs a change or an answer, followed by a short summary of the resulting behaviour and deployment impact. Every run renders the same shape — a review-only run, a code-review mirror, the post-convergence report, and the merge-readiness TL;DR alike — and `templates/pr-summary-jira.md` is where it is rendered:

1. **No status line opens the comment.** No sentence stands above the first heading: not the state of the work, not whether the change is ready to merge, and not that nothing was merged or deployed. A point that blocks the merge is a `Review findings` bullet.
2. **`Acceptance criteria` renders only for an explicit requirement that is unmet, partially met, or needs an answer before it can be accepted.** Each bullet states the missing change or answer and its evidence. Omit satisfied requirements, completion counts, and positive verdict sentences everywhere in the JIRA report. When every requirement is satisfied, omit the whole section. When the assignment states no explicit criteria, omit it too. The caller still supplies the full assignment verdict internally; the pull request retains its functional verdict.
3. **`Review findings` lists only the points that still need a change or an answer before the merge**, retold from the newest GitHub pull-request review. `SKILL.md` *Review-only run* owns the finding format and grouping. In a partially resolved finding, report only the remaining action; omit the repaired parts and their history. A point that blocks the merge comes first and says so in words. A security point that still needs verification blocks the merge: it is the first bullet, named as a blocker in plain words; its detail stays in the technical report. When no point needs action, use one sentence saying so.
   - An open decision that `verify-merge-readiness` or `april` passes keeps the question-and-recommendation shape its caller defines (`SKILL.md` *Review-only run*).
4. **`TL;DR` combines what changed and what deployment can affect in one paragraph of at most 600 characters.** State observable behaviour and the affected features in connected prose, in before → after form where useful. Include what a user should watch after release; omit mechanisms, repeated facts, and lists. The `Problem` / `Cause` / `Result` / `What I fixed` fields are not rendered on JIRA.
   - Source: the features the diff changes, plus the newest review's `## Affected behaviour outside the diff` (`@rules/code-review/core-analysis.md`), retold as features, never as files or methods.
   - When no code-review report exists for the current head yet, derive the parts from the diff and say the review has not confirmed them.
   - When the review report carries no `## Affected behaviour outside the diff`, list only the features the diff changes, with no caveat.
5. **The combined summary has the single heading `TL;DR` in every language.** It replaces the separate `What changed` and `Impact after deployment` sections.
6. **No `Clarifying questions` section on JIRA.** Each open question is the closing sentence of the bullet it belongs to. A question about an acceptance criterion closes that criterion's bullet in `Acceptance criteria`, and the criterion is then reported as unmet, partially met, or awaiting a human's confirmation. A question that concerns no criterion — a documentation mismatch, a blocking documentation request, a Critical decision outside the assignment, or any question on a ticket that states no explicit criteria — closes its `Review findings` bullet. A question may carry one recommendation sentence after it.
7. **No `How to test` on JIRA.** The steps a tester follows live on the GitHub pull request, whose description carries them (`@rules/git/pull-requests.md` *Testing*). The footer under the closing links line states that the comment is generated automatically and is written for the ticket owner.

`@rules/reports/general.md` *A JIRA comment is written for a non-technical reader* is binding on this comment. It lists the content that never appears in it, its exceptions, and the 3 000-character cap. Do not restate that list here — apply it.
