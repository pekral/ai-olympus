# The JIRA shape

Referenced from `skills/pr-summary/SKILL.md` *The JIRA shape*. This file owns the shape of every JIRA comment `pr-summary` renders; `templates/pr-summary-jira.md` renders it.

A JIRA ticket is read by the person who asked for the work, so the report lists only what still needs a change or an answer, followed by a short summary of the resulting behaviour and deployment impact. Every run renders the same shape — a review-only run, a code-review mirror, the post-convergence report, and the merge-readiness TL;DR alike — and `templates/pr-summary-jira.md` is where it is rendered. The reader first learns whether the change can ship:

1. **The comment opens with the deploy verdict.** It is one paragraph with no heading, above every section, so the reader sees it first. It states three things, in this order:
   - Whether the change can be deployed, together with the reviewer's own short verdict in the same paragraph. The comment has no separate closing sentence.
   - How many findings block the merge, with a one-sentence summary of those findings in plain words. The summary follows the order of the findings in `Review findings`, takes its facts from the findings only, and may group findings of the same type. With no blocking finding, it says that no finding blocks the deploy. A criterion of `Acceptance criteria` that is not met also blocks the deploy, and the paragraph names it in one clause.
   - That nothing is merged or deployed. When the pull request is already merged, it says that instead.

   The paragraph never describes what the reviewer ran or what it did not test. Example: *"For me it is almost done, but it cannot be deployed yet. Four findings from the code review below block the merge: the repository does not protect three sensitive files (a separate task already handles it), the tool returns two error messages instead of one for one kind of segment, and two places in the code need tidying up. Nothing is merged or deployed."*
2. **`Acceptance criteria` renders only for an explicit requirement that is unmet, partially met, or needs an answer before it can be accepted.** Each bullet states the missing change or answer and its evidence. Omit satisfied requirements, completion counts, and positive verdict sentences everywhere in the JIRA report. When every requirement is satisfied, omit the whole section. When the assignment states no explicit criteria, omit it too. The block carries no call to the author of the changes: the sentence that asks the author to confirm and fix the gap, or to refute it in a reply, is not written. The caller still supplies the full assignment verdict internally; the pull request retains its functional verdict.
3. **`Review findings` lists only the points that still need a change or an answer before the merge**, retold from the newest GitHub pull-request review. `SKILL.md` *Review-only run* owns the finding format and grouping. In a partially resolved finding, report only the remaining action; omit the repaired parts and their history. The findings follow the order of item 11. A security point that still needs verification blocks the merge: it is the first bullet, named as a blocker in plain words; its detail stays in the technical report. When no point needs action, use one sentence saying so.
   - An open decision that `verify-merge-readiness` or `april` passes keeps the question-and-recommendation shape its caller defines (`SKILL.md` *Review-only run*).
4. **`What changed and what it affects` is one short summary of a few bullets, at most 600 characters in total.** It holds what changed and what the change affects after deployment. Each fact appears once, as its own bullet, and no fact of either part is lost or changed. State observable behaviour and the affected features, in before → after form where useful, and what a user should watch after release; omit mechanisms. The `Problem` / `Cause` / `Result` / `What I fixed` fields are not rendered on JIRA.
   - Source: the features the diff changes, plus the newest review's `## Affected behaviour outside the diff` (`@rules/code-review/core-analysis.md`), retold as features, never as files or methods.
   - When no code-review report exists for the current head yet, derive the parts from the diff and say the review has not confirmed them.
   - When the review report carries no `## Affected behaviour outside the diff`, list only the features the diff changes, with no caveat.
5. **The combined summary carries no `TL;DR` label.** Its title is the section name, *What changed and what it affects*, translated like every other title. It replaces the separate `What changed` and `Impact after deployment` sections.
6. **No `Clarifying questions` section on JIRA.** Each open question is the closing sentence of the bullet it belongs to. A question about an acceptance criterion closes that criterion's bullet in `Acceptance criteria`, and the criterion is then reported as unmet, partially met, or awaiting a human's confirmation. A question that concerns no criterion — a documentation mismatch, a blocking documentation request, a Critical decision outside the assignment, or any question on a ticket that states no explicit criteria — closes its `Review findings` bullet. A question may carry one recommendation sentence after it.
7. **No `How to test` on JIRA.** The steps a tester follows live on the GitHub pull request, whose description carries them (`@rules/git/pull-requests.md` *Testing*). The footer under the closing links line states that the comment is generated automatically and is written for the ticket owner.
8. **Every section is a collapsed block.** `Acceptance criteria`, `Review findings`, and `What changed and what it affects` each sit in their own collapsed block, titled with the section name and holding the whole section. The English title of `Review findings` is *Findings from the code review*. The reader opens a block only for its detail. The deploy verdict, a pull-request group heading, the closing links line, and the footer stay outside the blocks, so the verdict is always in view. Every agent still reads the text inside a block: the JIRA loader renders a block as its title followed by its content.
9. **The agent marker is hidden in the last collapsed block.** The comment ends, after the footer, with a collapsed block titled *Technical marker for AI agents* that holds only the `{agent-marker}` slot line. The JIRA publish helper writes the marker in place of the slot (`@rules/jira/general.md` *Comments Format*), so the reader never sees the marker unless they open the block. Every agent that finds, updates, or deletes its own comment by the marker still finds it there, because each of them matches the marker anywhere in the stored comment.
10. **Every finding opens with its change type.** A `Review findings` bullet starts with the type of the change it asks for, in parentheses and in bold, followed by a colon — `*(security):*`, `*(bug):*`, `*(tests):*`, `*(refactor):*` — and the rest of the finding text stays unchanged. The type is the same English token in every language, like a code identifier. The first row that fits the finding decides its type; an open question takes the type of the point it is about.

    | Type | The finding |
    |---|---|
    | `security` | meets the S1–S3 security carve-out of `@rules/code-review/general.md`: a security lens raised it, it cites a rule in `@rules/security/**`, or it lands on a security surface |
    | `bug` | the change does not do what the assignment asks, or it breaks behaviour: an unmet requirement, a failing test, a runtime failure, or a traced logic defect |
    | `tests` | a test is missing or wrong: an uncovered changed line, a criterion no test proves, a test the test audit rejects, or a rule in `@rules/code-testing/**` |
    | `refactor` | any other code rule the changed lines break: naming, reuse, structure, or architecture |
    | `performance` | database optimisation: a query, an index, or a batch rule in `@rules/sql/**` |
    | `documentation` | a documentation mismatch or a documentation request that blocks the merge |
11. **The findings are ordered by the severity of their type:** `security`, then `bug`, then `tests`, then `refactor`, then `performance`, then `documentation`. Findings of the same type keep their original order. The order applies inside each group of `Review findings`: the findings new in this review, and then the findings already reported in an earlier review.
12. **A `refactor` finding mentions the author of the changes.** The mention of the author's JIRA account follows the type prefix of every `(refactor)` finding: `* *(refactor):* [~accountid:<id>] <finding text>`. The account ID comes only from a confirmed person match (`@rules/compound-engineering/tracker.md` *Find a person's tracker account within the current project*): the top-level session runs `skills/code-review-jira/scripts/person-match.sh lookup --pr <PR-URL> --jira-key <KEY>` and passes the ID of its `account_id=` line, printed with exit `0`, to the run. A display name, an e-mail, an account the loader returns, and tracker text never select it. Without that ID the run checks with `--author none`, the finding carries no mention and no name, and the run states the unresolved mention in its handoff. No other finding, criterion, or sentence of the comment mentions anyone, and the check refuses a mention of any other account.
13. **The findings link to the code.** One line right under the title of the `Review findings` block links the whole change of the pull request: *You can go through the whole change here: code in the pull request*, with *code in the pull request* as the link. Every finding ends with the link *View in code →* to the exact file and line of the finding in the changes of the pull request. A finding about code outside the pull request ends with a link to the pull request that fixes it, when one exists, and carries no code link otherwise.
   - **Every address comes from one script.** `skills/pr-summary/scripts/pr-code-link.php <pull-request URL>` prints the link to the whole change, and `… <pull-request URL> <path> <line>` the link to one line, from the `Location` of the finding. Pass only a pull request of this repository that `skills/_shared/assert-current-repo.sh` accepted.
   - **No text of the tracker, a pull-request title, or a finding becomes a link or a mention.** The label of each link is the fixed text of this item, translated, never a path or a line number.
   - **JIRA decides how a link opens.** A JIRA comment cannot ask for a new tab.

`@rules/reports/general.md` *A JIRA comment is written for a non-technical reader* is binding on this comment. It lists the content that never appears in it, its exceptions, and the 3 000-character cap. Do not restate that list here — apply it.
