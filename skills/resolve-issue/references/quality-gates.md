# Pre-push Quality Gates

Before committing and pushing changes, run project fixers and checkers on changed files. Discover available tooling using this priority:

1. **Phing** — check for `build.xml` or `phing.xml` in the project root. If present, list available targets (`phing -l`) and use relevant fixer/checker targets.
2. **Composer scripts** — if Phing is not available, inspect `composer.json` `scripts` section for fixer and checker commands (e.g. `fix`, `check`, `build`, `pint-fix`, `phpcs-fix`, `rector-fix`, `pint-check`, `phpcs-check`, `rector-check`, `test:coverage`).

Run in this order:
1. **Fixers** — run all available fixers on changed files (e.g. code style, rector, normalize). Fix any issues they report.
2. **Checkers** — run all available checkers/analyzers on changed files (e.g. code style check, static analysis, audit). Resolve all reported errors before proceeding.
3. **Coverage** — if a coverage command exists, run it and confirm 100% coverage for changed code paths.

If both fixers and checkers fail or are not found, stop and inform the user.

## Loop gate vs. final gate (issue #65)

A review/fix loop runs these gates **many times** — once per iteration — so the per-iteration gate must stay cheap without lowering the bar of the *merged* result. Distinguish the two:

- **Loop iteration (cheap, diff-scoped).** After applying a fix inside a review loop or a pre-PR self-check, run the **changed-files** variants only, and **skip the dependency/skill reinstall step** (`vendor/bin/agent-skills install --force`, `composer install`, `npm install`) — nothing the loop does changes the installed dependencies or skills, so reinstalling every iteration is pure latency. Prefer the project's diff-scoped scripts when they exist (`composer check:changed`, `composer test:coverage:diff`, or the equivalent) over the full `composer build` / `composer check`. Coverage is asserted **on the changed lines only** (never the full-suite `--min=100`) during a loop iteration.
- **Final gate (full, before push / PR).** Run the project's **full** build once — `composer build` (install + fixers + full `check`, including full-suite `--min=100` coverage) — as the last step before the changes are pushed or the PR is opened, and also whenever the change is **broad** (touches shared / core / config surface, or more than ~10 files — the same high-risk heuristic the `talos` scoped validation mode uses). This is the gate that guarantees a merge never lands with a broken project (issue #75); the loop lightening above never removes it, it only stops re-running it on every intermediate iteration.

The rule is one full build at the boundary, diff-scoped checks in the loop — not a full build per iteration, and not a merge on diff-scoped checks alone.

### CI-result reuse for the loop gate (issue #124)

The **loop iteration** gate above may skip re-running a check locally when CI already validated it — mirroring the "Reuse CI results when available" pattern already established for the coverage gate (`@rules/code-review/general.mdc` *Validation & Coverage Gate* → Coverage gate), extended here to the fixer/checker execution itself.

- **Reuse CI results when available, from structured provenance only.** Never decide reuse from the `context` / `state` fields of `statusCheckRollup[]` — that projection merges genuine GitHub Actions check-runs with legacy `repo:status` commit statuses into one indistinguishable shape (`skills/code-review-github/scripts/load-issue.sh` `map_status_checks`), so a forged status POST carrying a matching `context` and `state: success` is byte-identical, in that data, to a real Actions result. Resolve the verdict structurally instead: `gh run list --commit <sha>` to find the run for the commit, then `gh run view <run-id> --json jobs --jq '.jobs[].steps[] | {name, conclusion}'` (or `gh api repos/<owner>/<repo>/actions/jobs/<job-id>` for a single job) to read each step's real `conclusion`, matched by name to the local check it corresponds to — a project whose CI reports one combined check-run entry for several steps (as this repository's single `🔍 Quality Checks` job does) still exposes each step's own `conclusion` this way, so reuse is decided per resolved step, never assumed from the rollup's one combined entry. Never grep the human-readable run log (`gh run view` without `--json`) as a source of truth — its text (test output, package names, error messages) is PR-controlled and can imitate a passing line. Reuse only a step whose `conclusion` is `"success"`, on a run confirmed to be a genuine GitHub Actions workflow run of **this** repository — never a legacy commit status, never a foreign GitHub App's check. Record the provenance used (run id, job id, step name, `conclusion`, and the run's actually-checked-out SHA) the same way `@skills/merge-github-pr/SKILL.md` *Savings-mode cache reuse* requires provenance for a reused build result.
- **Reuse is forbidden when the diff redefines the gate itself.** Before trusting any CI result, check whether `.github/workflows/**` or the relevant `composer.json` `scripts` entries differ from the base branch. Any difference forbids reuse for every check those files define — the staleness guard below only proves a CI run's SHA matches the current commit, it says nothing about whether that exact commit's gate definition still means what an un-diffed definition would mean. A `pull_request`-triggered workflow runs the definition committed on the **PR's own ref**, so a step can be softened on a commit that still reports green under its unchanged name — e.g. adding `continue-on-error: true` to it, or replacing the script it calls with a no-op. This is not caught by reading structured step data either: GitHub reports a `continue-on-error`-suppressed failure's `conclusion` as `"success"`, identical to a real pass — diffing the gate definition itself against the base branch is the only defense against this vector.
- **`security-audit` is never reused, regardless of CI status.** Unlike this project's other CI-covered checks, `composer audit`'s verdict cannot be pinned to a commit the way the others can, for two independent reasons. (1) Its inputs — `composer.lock` and the installed `vendor/` tree — are untracked in the `laravel-agent-skills` repository (`.gitignore`), so "exact SHA on a clean tree" does not determine what packages it actually audits; an untracked dependency change can sit underneath a clean `git status` indefinitely, and CI itself never has a committed lockfile to check out either — `composer install` regenerates one, auditing a different package set than whatever is on a contributor's disk. (2) Independently of (1), `composer audit` queries a live advisory database at run time, so a green result is a function of *when* it ran, not only of *what* it read — yesterday's green run says nothing about an advisory published today; this reason alone would justify the exclusion even in a project that does track its lockfile. `security-audit` therefore always runs locally, every loop iteration, unconditionally — grouped in effect with the checks below that CI never runs at all, even though CI does run this one.
- **Staleness guard (mandatory, exact match — no heuristics).** Reuse requires a clean tree — `git status --porcelain --untracked-files=all` must be empty — and `HEAD` must equal that run's **actually-checked-out SHA** — as defined by the canonical **Staleness guard** sentence in `@rules/code-review/general.mdc` *Validation & Coverage Gate* → Coverage gate → "Reuse CI results when available" (that sentence's SHA-matching definition applies verbatim here even though it is stated inside the Coverage gate bullet: it defines what **actually-checked-out SHA** means and states the PR-side comparison against `headRefOid`; **the loop gate additionally requires the local `HEAD` to equal that actually-checked-out SHA**, because a locally committed but not-yet-pushed fix leaves a clean tree while `headRefOid` still points at the previous commit). A dirty tree disables reuse for **every** check without exception — there is no per-check "could not have affected it" carve-out; treat this as one strict rule, not a judgement call. The reused CI step must also have run a command at least as strict as the local check it replaces — for `test:coverage`, the same coverage threshold as the local gate (in this repository both are `--min=100`; a project consuming this file may configure them differently, so this must be verified, never assumed). **Note the practical reach:** a loop iteration that just applied a fix always has a dirty tree, so this reuse fires only on an iteration that changed nothing since the cited CI run — and never on `resolve-issue`'s own pre-PR gate, which runs before any PR (and therefore before any CI result) exists.
- **This repository's own CI can never satisfy the guard above — the reuse path is structurally unreachable here (issue #144).** `.github/workflows/pr.yml` is `pull_request`-triggered and checks out with a bare `actions/checkout@v4` — no `ref: ${{ github.event.pull_request.head.sha }}` — so on a PR event the action checks out the **merge ref** (`refs/pull/<N>/merge`), a merge commit that exists on neither branch, while the run reports `head_sha` = the PR's `headRefOid`. Both halves of that premise are the vendor's documented defaults, not an inference: the `ref` input of `actions/checkout` "defaults to the reference or SHA for that event" (<https://github.com/actions/checkout>, the `v4` the workflow pins), and that event reference is, for a `pull_request` that was not merged, `refs/pull/<pr_number>/merge` (<https://docs.github.com/en/actions/reference/workflows-and-actions/variables>, `GITHUB_REF`). Because the Staleness guard above requires a match against that run's **actually-checked-out SHA** — as the canonical sentence it cites in `@rules/code-review/general.mdc` *Validation & Coverage Gate* → Coverage gate → "Reuse CI results when available" defines that term — the match can never hold here, and every check therefore always runs locally in `laravel-agent-skills` itself. This is the correct conservative outcome — a non-match forces the local run and can never produce a false-positive reuse — and it is written down here so the dead path stays a known, deliberate state instead of something each reader rediscovers. Note the scope: the same workflow's `push: branches: [master]` trigger does check out the pushed commit, so it is only the **PR-side** reuse — the only side the loop gate would ever want — that is unreachable.
- **Do not "fix" the above by pointing the checkout at the head SHA.** Adding `ref: ${{ github.event.pull_request.head.sha }}` would make the guard matchable, but it trades a CI signal that validates the **merged** result for one that validates the branch in isolation — and it buys an optimization whose practical reach is already almost nil, because the Staleness guard also demands a clean tree, so reuse fires only on a loop iteration that changed nothing since the cited run, and never on `@skills/resolve-issue/SKILL.md`'s pre-PR gate (which runs before any CI result exists at all). Losing merge-result coverage is the larger cost by a wide margin, so the current workflow is deliberately left as it is. The reuse mechanism is written for a **consuming** project whose CI explicitly checks out `github.event.pull_request.head.sha`, or that runs its gate on `push`, where `GITHUB_SHA` is the pushed commit.
- **Checks CI never runs are never reused.** A project's own full local gate can include steps its CI workflow does not execute at all. As a concrete example, in the `laravel-agent-skills` repository `skill-check`, `composer-normalize-check`, and `shell-self-tests` are part of `composer.json`'s `@check` but are absent from `.github/workflows/pr.yml`'s steps, so they always execute locally regardless of CI status elsewhere. That is this repository's own example, not a portable list: the normative instruction for any project is to derive the actually-executed step set from that project's own cited CI run (`jobs[].steps[]`) rather than assume this exact set of names applies.
- **Failing / incomplete CI — never treat a non-green status as a pass.** A step is reused only when its `conclusion` is exactly `"success"`. Every other outcome blocks reuse — including `failure`, `cancelled`, `skipped`, `neutral`, `timed_out`, `stale`, `action_required`, a step or job reporting `completed` with no `conclusion` at all, and a step still `in_progress` / `queued`. Run it locally instead, or record the gap as a blocking finding.
- **Scope: loop gate only, never the final gate.** This reuse mechanism applies exclusively to the **Loop iteration** bullet in *Loop gate vs. final gate* above — never to the **Final gate** bullet in that same section, regardless of which consuming skill's own section happens to share the heading "Pre-push quality gates" (`@skills/resolve-issue/SKILL.md` and `@skills/process-code-review/SKILL.md` both use that exact title for sections with different scope — the former's is the **final** gate, the latter's is the **loop** gate). A freshly authored, not-yet-pushed commit has no CI result at all — there is nothing to reuse until it is pushed and CI completes — so this repository's own root `CLAUDE.md` mandate ("before push run `composer build` and fix all errors, never ignore errors!"), or a consuming project's equivalent pre-push mandate, is never weakened by this optimization.

### Savings-mode build-gate cache (opt-in, issue #119)

When a shared task brief is present and records `## Savings mode: on`, the **final gate** above may cite a cached passing result from the brief's `## Build gate cache` instead of re-running. The canonical hash definition (a **tree** hash via `git rev-parse "$(git stash create)^{tree}"`, mixed with non-tracked build inputs such as `composer.lock`), the hit / miss / failing-entry semantics, and the per-brief append lock all live in `@rules/compound-engineering/general.mdc` *Savings mode* mechanism 2 — this file adds only the local condition: the mechanism applies to this file's own **final gate** (never the diff-scoped loop gate), and a fresh full run's result is appended here exactly as that mechanism describes.

**This never applies to the mandatory full run on the exact final head SHA immediately before merge** (`@skills/merge-github-pr/SKILL.md` *GitHub Actions billing exception*) — a cache hit is acceptable there only under that skill's own *Savings-mode cache reuse* provenance requirements. Any run with savings mode off, or with no shared brief at all (no `daidalos` orchestrating the run), always executes the final gate in full, exactly as before this mechanism existed.
